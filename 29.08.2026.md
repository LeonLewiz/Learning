# Мой отчет за День 5: Собрал нормальный CI/CD на GitHub Actions. 27 и 28 отдыхал, были только организационные моменты (сделал работу удобнее, поставив несколько утилит (htop и lazydocker, последний еще не пробовал и наверное не буду.)


## Что было сделано

### 1. Разобрался с CI/CD на пальцах (GitLab → GitHub)

Сначала начал с **GitLab CI**: понял, что такое pipeline, stage и job, как они связаны между собой. Но зарегистрироваться на GitLab.com с нашего телефона не вышло — отрубили номера из РФ.

Не растерялся и перешел на **GitHub Actions**, а там та же логика, только другие названия. По сути выучил концепцию, а не кнопку. Это порадовало, потому что в проде чаще встречается GitLab — а я теперь знаю базу.

### 2. Написал свой первый workflow

Создал файл `.github/workflows/ci.yml` в корне репозитория. Сначала просто `echo` + `ls`, чтобы понять, как открывается вкладка Actions и как читать логи запуска. Потом добавил **сборку Docker-образа** из `./backend` прямо в CI.

Уяснил, что раннер (`ubuntu-latest`) — это временная виртуалка GitHub: образ, собранный там, исчезает после джобы. Поэтому образы надо куда-то складывать.

### 3. Научился кидать образы на склад (GHCR)

Подключился к `ghcr.io` через встроенный токен GitHub (`GITHUB_TOKEN`), он создается сам на каждый запуск. Запушил образ на склад: `ghcr.io/leonlewiz/my-nginx-site/my-test-image`. Теперь образ лежит в Packages на GitHub и доступен отовсюду.

### 4. Поднял self-hosted runner на своей виртуалке

Сначала попробовал деплой через SSH-шаг (GitHub сам заходит на сервер), но виртуалка в NAT, и из интернета на нее не подключиться.

Правильным решением оказался **self-hosted runner**: сама виртуалка стала исполнителем. GitHub просто дает ей команды, она выполняет у себя и отчитывается.

Запустил runner через `./run.sh`, потом превратил его в системную службу (`svc.sh install/start`) — теперь он в фоне.

В workflow поменял `runs-on: ubuntu-latest` на `runs-on: self-hosted`.

### 5. Замкнул весь цикл: пуш > сборка > на склад > деплой

Теперь когда я пушу в `main`, CI сам: подтягивает код > собирает образ > шлет его в GHCR > обновляет контейнеры на виртуалке.

Проверял, что работает: `docker images` на VM, `docker inspect` контейнера, сравнение ID образов. ID совпадает со складским.

### 6. Ускорил сборку кэшем

Поначалу стоял `--no-cache` _ 40 секунд на каждый пуш, все apt и pip ставились заново. Убрал флаг, runner у меня свой, кэш Docker остается на диске между запусками, теперь пересобирается только слой с кодом. **Сборка упала до 18 секунд.**

## Разбор ошибок (чтобы не наступать на грабли)

| Ошибка | Что я понял |
|---|---|
| `repository name must be lowercase` | Docker и реестры не любят заглавные буквы в именах. У меня `LeonLewiz`, пришлось приводить к `leonlewiz`. |
| `An image does not exist locally with the tag` | Собрал образ как `my-test-image`, а пушить пытался как `ghcr.io/...`, это два разных «имени». Нужен `docker tag` перед пушем. |
| `denied: installation not allowed to Create organization package` | Встроенный токен GitHub по умолчанию умеет только читать. В настройках репозитория включил **Read and write permissions**, все заработало. |
| `i/o timeout` по порту 22 | Нельзя достучаться до NAT-виртуалки из интернета. Перешел с SSH деплоя на self-host. |
| ID образа не менялся | Сначала думал, что деплой не работает. А оказалось, что код не менялся, Docker кэширует слои по содержимому. Изменил `main.py`, ID сменился. |
| Деплой подтягивал старый код | В деплой-шаге не обновлялась папка проекта на диске. Добавил `git pull` перед `docker compose up`. |

## Итог

У меня теперь **production-цикл**: `git push origin main` → GitHub сам собирает образ > кладет на склад > мой self-hosted runner на виртуалке подтягивает и перезапускает контейнеры. Сборка 18 секунд. Сайт все еще работает на `http://192.168.13.130:9090`, счетчик работает.
